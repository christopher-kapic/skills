# Watch-list: Persisted state machines

Attach when the diff adds or changes a persisted status or state column, a job or attempt lifecycle, retries, expiry, reapers, or reconciliation.

Apply after coverage enumeration, using the common worker brief's reporting format and the supplied evidence rules.

- **SM1 Production trigger for every transition.** Does every required transition (revoke, wake, cancel, ack, expire, release, terminalize) have a production caller, not only a function or a test? **Verify:** for each target state and each emitted event, search for writers and emitters outside tests. A function with zero production callers, or a notification that no code emits, is a finding.
- **SM2 Retries reach a terminal state.** Does every retry, expiry, lease-reclaim, or redrive loop have a budget and backoff that end in a terminal failure state? **Verify:** force a permanent failure and count iterations, or trace the counter from where it increments to where it is checked.
- **SM3 Terminal and priority states are protected.** Can a later or competing outcome overwrite a terminal or higher-priority state (for example, progress over cancel-requested, cancelled over a natural exit, a stale plan over a newer one)? **Verify:** confirm that every transition write names its allowed from-states in the predicate. Construct the race where both outcomes arrive, in both orders.
- **SM4 No stranded intermediate state.** For each intermediate state (creating, stopping, running, pending, committing), what moves it forward after a crash, cancel, throw, 4xx, or lost ack? **Verify:** inject a failure at each step. Check that a reaper or recovery path selects that state and that the path is itself triggered (see SM1).
- **SM5 Outcomes need evidence.** Is each state that asserts a fact (cancelled, deleted, succeeded, released, terminated) written only with proof of that fact? Do ambiguous observations map to unknown rather than to success or failure? **Verify:** for each such write, name the evidence it relies on. Check that pruning or cleanup does not delete evidence that a later transition needs. Check that late output after an observed exit is still drained before success is reported. Check that retries record the original event's time and outcome, not the retry's.
- **SM6 Gates cover every entry point.** Do blocking states (repair-required, quarantined, disabled, deleting) block every entry point, including reads, fallbacks, and new work that would overtake unfinished work? **Verify:** list the entry points that touch the object and confirm each one checks the gate, including filesystem or cache fallbacks.
- **SM7 Sticky flags.** Does a flag set once (handed off, trusted, initialized) relax a check in later states where the strict check matters again? **Verify:** list each flag's writers and resetters, then walk the states after it is set and ask whether the relaxed check is still valid.
- **SM8 Temporary failures stay recoverable.** Can a timeout, unavailable dependency, or ambiguous lookup permanently mark an object absent, revoked, invalid, or complete without authoritative evidence? **Verify:** fail the dependency once, restore it, and retry through the real caller. Check that recovery remains reachable and that cleanup has not discarded late-attempt evidence needed to settle the outcome.
