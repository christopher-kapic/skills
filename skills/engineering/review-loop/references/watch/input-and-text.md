# Watch-list: Input validation and text

Attach when the diff parses or validates external input, persists or renders user strings, builds identifiers, paths, argv, or headers, runs user-influenced regular expressions, or scans or redacts content.

Apply after coverage enumeration, using the common worker brief's reporting format and the supplied evidence rules.

- **IT1 Values in argv.** Can a value passed to a subprocess be read as an option? **Verify:** find every argv construction that includes an input value and try a value such as `--output=/tmp/x`. Leads: `--` ends options only for getopt-style positional arguments, and in git everything after `--` is a pathspec, so revisions need `--end-of-options` (git 2.24+) or a value that is rejected when it starts with `-` (see git-plumbing GP6).
- **IT2 Injection into structured text.** Are values placed into headers, quoted strings, or line protocols escaped for quotes, backslashes, `<`, `,`, CR/LF, and control characters? **Verify:** run a table of hostile values through the real serializer and parse the output back.
- **IT3 Types and control characters.** Are wrong JSON types, NUL, and C0 controls rejected at the boundary with a client error, rather than reaching the database and returning a 500? Does each field's contract say which format characters it allows? ZWJ and ZWNJ (category Cf) are required by emoji and several scripts, while bidi overrides are a display concern. **Verify:** send U+0000, a C0 control, U+200D, U+202E, and non-string values to each string field and compare the results with the field's contract.
- **IT4 Length caps before persistence.** Does every attacker-controlled field (names, filenames, MIME types, IDs, log fields, third-party responses) have a cap before it is stored, logged, or echoed? **Verify:** send a very large value to each field and follow where it lands.
- **IT5 Validate the final form.** Do validation, identity comparison, and use all see the same final representation? Input that is validated before a later decode, normalization (NFC/NFKC), trim, case fold, or percent-decoding can become dangerous afterwards; fullwidth `．．／` becomes `../` under NFKC. **Verify:** list the transformations between the boundary and use. Validate after the last one, or reject input that a later transformation would change. Reject invalid encodings rather than replacing them. Try fullwidth and compatibility forms, percent-encoding, invalid UTF-8, a leading BOM, and NBSP at the ends.
- **IT6 Structural canonicality.** Are duplicate entries, unsorted collections that must be sorted, empty names, embedded separators, and names reserved by the target system (`.`, `..`, device names) rejected? **Verify:** create a fixture for each case against the validator. For git trees, see git-plumbing GP1.
- **IT7 Regex semantics.** When patterns are user-supplied or derived from user input, do escapes, anchors, character-class ranges, and escaped range endpoints mean what the spec says? **Verify:** run a differential test against a reference engine, including anchored, escaped, and wide-range patterns.
- **IT8 Hand-written parsers for standard formats.** Does a restricted parser for YAML, MIME, Markdown links, and similar formats either parse each construct correctly or reject it explicitly (anchors, aliases, flow style, folded scalars, nested multipart, relative links)? **Verify:** feed a conformance corpus that includes the unsupported constructs, and expect either a correct parse or an explicit rejection.
- **IT9 Scanners see what consumers see.** Do secret scanners, redactors, and filters inspect the representation the consumer interprets, across every field that is persisted or sent (titles, keys, comments), and in every escaping form (quoted, escaped, tab-separated, leading whitespace, `Bearer <token>`)? **Verify:** encode a known literal in each form the output format allows and check detection.
- **IT10 Units for text length.** Does each length limit name its unit (UTF-8 bytes, UTF-16 code units, Unicode scalars), and do the runtime check, generated schema, database column, and docs agree on it? **Verify:** test at the boundary with multi-byte and astral characters, one step on each side.
- **IT11 Case folding and normalization.** Is full Unicode case folding used rather than lower-casing? Is it idempotent, does it cover multi-character folds, and is it applied to directory prefixes as well as leaf names? **Verify:** test σ/ς/Σ, ß/ss/ẞ, ᾀ/ἀι, and Cherokee pairs, and assert `fold(fold(x)) == fold(x)`.
- **IT12 Timestamps as instants.** Are timestamps parsed and compared as instants, with invalid values rejected and the precision the spec allows preserved? **Verify:** compare `Z` with `+00:00`, and test sub-millisecond values and invalid dates.
- **IT13 Unforgeable sentinels.** Can user content or a nested program's output contain the placeholders, markers, delimiters, or control sequences that the code later substitutes, splits, or keys state on (for example, a terminal parser keyed on an escape sequence that an editor inside the session also emits)? **Verify:** ask what else can produce the same bytes, then emit them from user content or a child program and check the output and state.
- **IT14 Pasted rich text is untrusted.** Do paste, drag/drop, import, editor serialization, persistence, and later rendering apply the required HTML/URL policy even when typing is constrained? **Verify:** paste rich content with event handlers, dangerous URLs, and encoded markup through the actual editor; save and reopen it through each renderer. Confirm sanitization is active in the test runtime (test-adequacy TA10) and that later transformations do not restore unsafe content.
