# Watch-list: Resource budgets and denial of service

Attach when the diff adds or changes limits, quotas, rate limits, size caps, step or CPU budgets, queues, caches, batch sizes, or processing of attacker-sized input.

Probe after the coverage table. Confirm the application's contract first; a mismatch with an entry alone is not a finding. Named APIs are leads, not accepted fixes. `verified` closure needs a probe of the property; report a step you cannot run safely as not run. Report `ID: evidence`, a finding, or `ID: n/a`.

- **RB1 Every path is charged.** Does every path to the resource charge the same budget, including fast paths, non-matching and anchored matches, recursive walks, decoded or re-encoded streams, and secondary operations such as accept, transfer, or share? **Verify:** enumerate the entry points to the resource and, for each one, send input just over the limit.
- **RB2 Budgets cover the whole operation.** Does the budget accumulate across the whole operation instead of resetting per loop iteration, commit, page, or retry? **Verify:** run many small iterations whose total exceeds the limit.
- **RB3 Charges are exact.** Is each unit counted exactly once, with nothing double-counted (paired or lineage items, directory entries, exact-limit items) and nothing under-counted (fixed allowances, pre-existing items charged as new)? After an under-count fix, check for over-count. **Verify:** test exactly at the limit, with unchanged items, and with paired items.
- **RB4 The ledger follows failures.** Do charges and releases on reject, abort, tombstone, recovery, restart, and retention match what actually remains stored or allocated? **Verify:** after each failure path, compare the ledger with the real storage or slot count.
- **RB5 Work stays linear.** Can attacker input cause rescans, regex backtracking, or nested loops that grow faster than linearly? **Verify:** time the operation at 10× and 100× input size. Look for rescans after a failed delimiter match and for nested quantifiers.
- **RB6 Queues and caches are bounded.** Are receive queues, pending maps, in-memory limiters, and lifetime counters bounded, and do their entries expire? **Verify:** flood the producer with no consumer and check memory and expiry.
- **RB7 Platform limits apply to the final form.** Are platform limits (bind parameters, token or cursor size, response envelope, line length) checked against the final serialized form, not an intermediate one? **Verify:** send the largest allowed input and measure the serialized output.
- **RB8 Amplification is bounded.** Does one request produce a bounded number of rows, audit events, wakeups, and fan-out expansions? **Verify:** send a request that touches N hidden or related items and count the writes.
- **RB9 Caps amplify leaks.** Can a small per-attempt leak (a parked blocking thread, an unclosed fd, an unreleased permit) exhaust a process-wide cap (blocking-thread pool, fd limit, semaphore, connection pool) and stall unrelated work? **Verify:** find the caps the leaked resource counts against, then loop the leaking path past the cap.
