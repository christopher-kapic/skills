# Watch-list: Durability, crash ordering, and recovery

Attach when the diff has effects that must survive a crash: file or object writes, fsync, external API side effects, outboxes, publish or commit protocols, recovery, reconcile, or garbage collection.

Probe after the coverage table. Confirm the application's contract first; a mismatch with an entry alone is not a finding. Named APIs are leads, not accepted fixes. `verified` closure needs a probe of the property; report a step you cannot run safely as not run. Report `ID: evidence`, a finding, or `ID: n/a`.

- **DR1 Durable intent before effect.** Before each external effect (publish, provider call, send, ref update, spawn), is an intent record durable that lets recovery find and settle the effect? **Verify:** for each effect, name its intent record. Simulate a crash between intent and effect, and between effect and completion, then run recovery.
- **DR2 Validate before durable write.** Is input validated and charged before anything durable is written, so that a rejection leaves no orphaned, uncharged, or promoted artifact? **Verify:** submit input that fails the last validation step, then list what remains in each store.
- **DR3 Durability errors propagate.** Do errors from fsync, directory fsync, close, and rename reach the caller, and is success reported only after the data and the directory entry are durable? **Verify:** search for `catch` or ignored results around these calls. Inject EIO through a fault hook where one exists. Lead: after fsync fails, a retried fsync can succeed even though the data was dropped, because Linux marks the pages clean. Treat the failure as fatal for that file or state, never as retry-until-success.
- **DR4 Crash leftovers are cleared.** After a SIGKILL mid-operation, does recovery clear lock files, temp files, partial uploads, staged rows, and prepared references, and can it collect the loser of a race? **Verify:** kill the process at each step in a test, run recovery, and assert a clean state and a retry that succeeds.
- **DR5 Recovery is atomic and re-runnable.** Is each object's reconcile one transaction? Can recovery or replay crash halfway and run again (idempotent DDL, no duplicate-constraint failures)? **Verify:** kill recovery midway and rerun it. Run replay twice.
- **DR6 A retried create keeps its identity.** Does an interrupted create, retried with the same key, resolve to the same object and ID instead of allocating a new one? Is lookup-then-insert replaced by a conditional insert? **Verify:** interrupt a create after allocation, retry it, and count objects.
- **DR7 Recovery spares live work.** Can orphan cleanup, expiry, garbage collection, a backfill, or retention act on work that is still in progress (preparing, uploading, mid-retry, dispatched by a predecessor)? **Verify:** run each sweep concurrently with a slow in-progress operation, and check the predicate the sweep uses to decide that work is abandoned.
- **DR8 Persisted and observed state agree.** Where two sources of truth exist (filesystem versus database head, object store versus index), is divergence detected even when no intent is pending? **Verify:** diverge them manually and run startup or reconcile.
