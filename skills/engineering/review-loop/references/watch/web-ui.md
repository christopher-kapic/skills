# Watch-list: Web and browser UI

Attach when the diff touches browser-rendered forms, nested controls, navigation or app shells, asynchronous UI state, client/server flows, error copy, pending states, or settings that change safety or autonomy. This list targets web UI, including browser-based desktop shells; do not attach it solely for native GUI or terminal UI changes.

Apply after coverage enumeration, using the common worker brief's reporting format and the supplied evidence rules.

- **UI1 Nested controls do not trigger unintended effects.** Can Enter in a search, tag editor, dialog, or other nested input submit an outer form or activate a default action unexpectedly? **Verify:** exercise keyboard Enter from each nested control in a real browser and count submitted requests. Check button types, event propagation, and the intended keyboard action.
- **UI2 Newer intent owns the visible state.** Can a late response, validation, navigation cleanup, or optimistic rollback overwrite a newer selection, URL, draft, or request result? **Verify:** delay request A, complete B, then settle A in both success and failure forms. Navigate or unmount during the wait; assert that newer state and ownership survive and relevant late-attempt evidence is retained.
- **UI3 Required screens are reachable.** Can the intended roles reach every required screen through the application shell and return or deep-link as promised? **Verify:** map required screens to actual routes and shell controls, then navigate from the normal entry point for each role. A component rendered only in isolation is not reachability evidence.
- **UI4 Flows agree with real server contracts.** Does each changed UI flow call the handler with its actual parameter names, method, headers/body, credentials, and response shape? **Verify:** complete the flow against the real route using production client helpers without intercepting the route under test; include rejection paths. Apply errors-and-contracts EC10 for omitted-body mutations.
- **UI5 Errors and pending states reach the user.** Does server error copy survive mapping layers into visible, actionable feedback, and are pending states shown while work is unresolved? **Verify:** trigger real validation, permission, and temporary failures and stall a request. Inspect the rendered message, pending affordance, retry behavior, and whether accidental duplicate submission is prevented where required.
- **UI6 Risky settings communicate their effect.** Are settings that broaden permissions or permit unattended actions visibly explained at the decision point, including the current enabled state? **Verify:** walk the enable/disable flow and inspect the actual copy and persistent indicator against the recorded product decision. Do not invent a new confirmation requirement; check that the intended risk and scope are understandable.
