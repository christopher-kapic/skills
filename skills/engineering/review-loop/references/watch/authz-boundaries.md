# Watch-list: Authorization boundaries

Attach when the diff touches authentication, authorization, roles, grants, sharing, capabilities, tokens, sessions, admin actions, idempotent replay, or exported modules that own policy.

Probe after the coverage table. Confirm the application's contract first; a mismatch with an entry alone is not a finding. Named APIs are leads, not accepted fixes. `verified` closure needs a probe of the property; report a step you cannot run safely as not run. Report `ID: evidence`, a finding, or `ID: n/a`.

- **AB1 Authorize at the moment of effect.** Is authorization (revocation, ban, role, forced 2FA, grant, sender or address ownership) re-checked inside the transaction or CAS that commits the effect, and before any destructive step? **Verify:** find the gap between authorize and commit. Revoke, ban, or demote inside that gap (pause point or hook) and expect denial with no partial effect and no success audit.
- **AB2 Authorize at the return boundary.** Do list and get re-check authorization on the rows actually loaded, applying it before `LIMIT` and pagination rather than after? **Verify:** revoke one item mid-assembly. Seed more unauthorized rows than a page holds and check that authorized rows are not hidden.
- **AB3 Every replay path re-authorizes.** Do idempotent-receipt replay, queued retries, cached responses, and pending commits re-run live authorization and verify the request hash? **Verify:** search for every receipt, idempotency, and queued-work lookup, and treat each as a separate path, because this class often reappears on a second and a third path. For each path, revoke and then replay.
- **AB4 Capabilities stay narrow.** Can a narrow capability (send-only, read-only, worker, delegate) reach broader operations such as decrypting, minting, managing, or registering its own identity? **Verify:** build an actor × operation matrix and test every denied cell, including revoked actors.
- **AB5 Approvals bind their object.** Is an approval or consent bound to the exact object and parameters it approved (slug, device, recipient, permissions)? Can an old idempotent retry change them? **Verify:** approve X and redeem it for Y. Replay an old request after the object changes.
- **AB6 No production bypass.** Can exported helpers, test hooks, opt-in bypass flags (`allowPrivateNetworks`, `skipValidation`, `unsafe…`), raw default transports, or alternate chokepoints be reached from production code? **Verify:** list the exports of every module that owns policy, and trace each one to production entry points or show it is unreachable.
- **AB7 Library endpoints grant only what is intended.** Which routes do an auth or framework library and its plugins mount, what does each one grant, and does your policy run before any destructive effect? For example, a device-flow token endpoint may issue a full browser session. **Verify:** enumerate the mounted routes from configuration and library source, then call each one as a half-approved or unprivileged actor. For auth-library hook paths, see auth-libraries.
- **AB8 Patterns are not owned literals.** Are wildcard or pattern values (`*.domain`, resource patterns) prevented from being adopted, deleted, or fenced as though they were concrete owned names? **Verify:** submit wildcard values to each create, adopt, and delete path, and check grant fences against patterns.
- **AB9 No cross-scope effects.** Can an operation read, join, or change another tenant's, domain's, or container's objects, or skip a per-scope disable flag? **Verify:** create two scopes and attempt each operation across them.
- **AB10 Secrets and attempts are scoped.** Is each signing or HMAC key domain-separated per purpose? Do attempt limits cover every credential path (recovery codes, OTPs, device codes)? **Verify:** present a token minted for purpose A at endpoint B. Count guesses allowed per challenge on each path.
- **AB11 Guards fail closed.** Does a guard that gates a safety or exclusion step skip that step when its own check errors, through an error-swallowing combinator, optional chaining, or a catch-all that returns success, for example over a path that was renamed or removed after the check? **Verify:** search for fallible calls inside security or exclusion conditions, make each call fail (remove or rename the target between check and use), and confirm the step fails closed. For Rust idioms, see rust RS3.
