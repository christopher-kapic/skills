# Watch-list: Concurrency and shared state

Attach when the diff touches state that more than one actor can write: database rows, locks, leases, version or CAS columns, idempotency keys, claims, reservations, queues, workers, or retries.

Probe after the coverage table. Confirm the application's contract first; a mismatch with an entry alone is not a finding. Named APIs are leads, not accepted fixes. `verified` closure needs a probe of the property; report a step you cannot run safely as not run. Report `ID: evidence`, a finding, or `ID: n/a`.

- **CS1 Check-then-act.** Does every write that depends on a read (status, existence, permission, balance, free space, prior classification) rest on a named concurrency guarantee: a lock held from read to write, a conditional write that re-checks the value (version column, `WHERE` predicate, CAS), a unique constraint, or serializable isolation with retry? A shared transaction alone is not a guarantee at common default isolation levels (see sql-databases DB11). **Verify:** list each read→write pair in the changed code and its callers and name its guarantee. For each gap, write out the interleaving where another actor changes the value in between. Where a harness exists, run two concurrent callers.
- **CS2 Values sampled before the lock.** Are clocks, deadlines, budgets, and measurements that a decision uses taken after acquiring the lock the decision runs under? **Verify:** search for clock and measurement reads (`now()`, `Date.now`, `Instant::now`, free-space or size queries) above each lock or transaction start, and trace them to the decisions made inside.
- **CS3 One-time consumption.** Is every one-time token, code, approval, claim, or reservation consumed exactly once, with the code acting on the state it consumed rather than on a separate re-read? **Verify:** run two concurrent redeems of the same item, and two different items against the same parent (for example, two recovery codes on one challenge). Exactly one should succeed, and nothing should be burned without an outcome. Leads: a conditional `UPDATE … RETURNING` or `DELETE … RETURNING`, a row lock held to the write, or an atomic compare-and-swap.
- **CS4 Concurrent duplicates and key scope.** Does a concurrent duplicate request get the outcome the idempotency contract promises (typically the original's result), rather than a unique-violation 500 or an undocumented conflict? Are idempotency and dedup keys scoped to actor, resource, and purpose, so that distinct callers can't collide and user keys can't enter internal key namespaces? **Verify:** fire two identical requests concurrently. Reuse one key across two actors and across two resources. Send a key with an internal prefix.
- **CS5 Fresh fence per attempt.** Does every new attempt (retry, recovery, republish, reconnect, replacement) get a new epoch or generation, and does the side that performs the effect compare it? **Verify:** enumerate every path that restarts work and confirm it increments the fence. Then find the consumer-side check. A fence the executor never reads does not count.
- **CS6 Stale actor versus successor.** Can an older attempt, consumer, cleanup, or delayed job release, clear, overwrite, or delete a lock, lease, protection, intent, rule, or slot that now belongs to a successor? **Verify:** check that every release, clear, and delete is conditioned on the owner identity or epoch it acquired with. Construct the case where A stalls, B takes over, and then A finishes.
- **CS7 Identity, not names.** When adopting, reconnecting to, signalling, or mutating an existing resource by name, ID, PID, or timestamp, does the code verify an identity tag, nonce, or generation? **Verify:** create a same-named foreign resource, or recycle the ID, then run the adopt, stop, kill, and file paths against it.
- **CS8 Parallel form of a sequential fix.** When a fix validates something incrementally (lock order, cumulative budget, claim), does the fix still hold when two calls interleave? **Verify:** run the fixed path from two concurrent callers, not only in sequence.
- **CS9 Protocol ordering.** Where control and data messages share a channel (cancel versus dispatch, stdin chunks, final chunk), can one overtake another, be duplicated, or be reordered? **Verify:** find the per-channel ordering guarantee in code, then send interleaved messages and check the order the receiver sees.
- **CS10 Lost wakeups.** Is every store to state that a loop waits on followed by a notification (watch, notify, condvar, channel send), on every path including rollback and error paths, and does the waiter re-check the state before parking? **Verify:** list the writers of each awaited value and check each for a notify. Force the rollback path and see whether the waiter wakes.
- **CS11 Shortcuts that skip a check.** When code skips check B because condition A supposedly implies it, does A imply B on every path, including successors, races, and later states? **Verify:** state the implication, then look for a path where A holds and B fails.
