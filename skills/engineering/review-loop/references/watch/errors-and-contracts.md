# Watch-list: Errors, contracts, and third-party behavior

Attach when the diff touches error types, codes, or mapping layers, wire protocols, schemas shared between components, generated artifacts, version negotiation, or calls into a third-party library, CLI, or API.

Apply after coverage enumeration, using the common worker brief's reporting format and the supplied evidence rules.

- **EC1 Classify by type, not text.** Are errors classified by type, code, or structured field, rather than by message substring or parsed stdout and stderr? **Verify:** search for `.message`, `includes(`, and regexes over error or subprocess output. Craft input whose text contains the keyword being matched.
- **EC2 Wrappers preserve the kind.** Does each catch or wrap layer preserve the error type and cause, instead of relabeling unrelated failures (as connection lost, conflict, unknown outcome, or unavailable)? Do cleanup branches that depend on the kind still see it? **Verify:** inject each error kind at the lowest layer and assert the kind at the top, including in the cleanup branch.
- **EC3 Specific codes match the evidence.** Is a specific code (not found, gone, permission) returned only when the evidence supports it? **Verify:** table-drive the mapping over every errno or status that the lower layer can return.
- **EC4 Domain errors are client errors.** Does each domain error (quota, rate, conflict, validation) reach the client as that error, rather than as a 500, and do error builders restrict details and retryability flags? **Verify:** trigger each domain error through the real router or handler.
- **EC5 Both sides of a contract agree.** Does every error code, enum value, or field added on one side exist in the other side's schema or decoder? Is the parity check exhaustive (generated or compile-time) rather than a hand-maintained list? **Verify:** diff the enums across the languages involved and check how the other side handles an unknown value.
- **EC6 Breaking changes bump the version.** Does a breaking wire change bump the protocol version, so that old peers are rejected at handshake? **Verify:** connect a peer on the previous version.
- **EC7 Generated artifacts are faithful.** Are generated schemas and types non-empty, do they carry runtime refinements, and can the drift check see custom validators? **Verify:** validate a known-invalid corpus against the artifact and expect rejection.
- **EC8 Third-party behavior is verified.** Are units (ms or s), accepted flags per subcommand, which hooks fire on which paths, upsert and conflict semantics, and defaults verified against the pinned version's source, documentation, or a probe? **Verify:** cite the source location or run the command or query. An assertion from memory is a concern, not evidence.
- **EC9 Documented claims hold.** When a doc comment, commit message, or UI text states an invariant ("X never appears in Y", "always Z"), does the rest of the codebase agree? **Verify:** search the codebase and UI for counterexamples to each claim the diff adds or relies on.
- **EC10 The real client request fits the handler.** Do mutating requests work exactly as the production client helper builds them, including method, URL, headers, content type, omitted versus empty body, credentials, and response parsing? **Verify:** send each changed mutation through the real helper and router without mocking that route. Include a bodiless mutation where supported and compare with the handler's actual signature and middleware requirements; direct handler calls alone miss transport mismatches.
