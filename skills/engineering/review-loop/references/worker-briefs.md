# Worker briefs

The coordinator pastes the common brief and assigned role's brief verbatim into each prompt, with run-specific settings and the **Evidence states** section from [run-artifacts.md](run-artifacts.md). Include its fix-proof procedure when applicable. Critics also receive the reviewer brief. These are pass instructions, not invitations to start another loop.

## Common brief

1. Perform only the assigned pass. Do not invoke another harness, delegate, re-enter the review loop, or wait on stdin. Honor supplied time, memory, concurrency, and test-lifecycle limits. Coordinate heavy commands; do not run destructive checks against shared services.
2. Do not mutate the git index, refs, stash, or checkout, or run reset/clean/restore operations in the shared repository. Do not discard other work. Implementers may edit task files; reviewers and critics keep source read-only. Mutating experiments and deliberate breaks belong in isolated scratch copies. Report unexpected repository changes immediately.
3. If clock and file access are available, aim to write an `IN_PROGRESS` skeleton early (within 10% of the budget, capped at five minutes), append findings as they arrive, and stop new exploration around 70% to finish evidence and reporting. These are guidelines, not validity thresholds. Otherwise return the report through the available channel for the coordinator to preserve. State unfinished work explicitly; a skeleton, empty response, or exit code alone is not success.
4. Reuse recorded decisions and relevant recurring classes/carry-ins within the agreed scope. Name assumptions and conflicts before coding or judging behavior. Report actual commands, selected tests, results, revision, and limitations. End with explicit completion and a verdict appropriate to the role. `CLEAN` requires completed assigned coverage with no unresolved required findings or evidence gaps; otherwise report findings, unverified, or incomplete. A critic's last line follows its special format.
5. Use the supplied evidence schema. For each applicable watch-list entry report `ID: holds (executed) — command/result`, `ID: holds (structural) — cited proof/bound`, `ID: reviewed — static evidence`, `ID: violates — finding`, `ID: unverified — missing evidence`, or `ID: n/a — contract-based reason`. Confirm the application's contract before treating a list mismatch as a finding. Named APIs are leads, not accepted fixes. Do not substitute structural evidence where the boundary requires execution.
6. Severity calibration: in-scope defects causing exploitable violations, unintended data loss, persistent corruption or stranding, broken deployment, or unmet required behavior are blockers regardless of rarity, or of the actor's privilege when the action exceeds that actor's authorized capability. Intended destructive actions within the agreed capability are not defects. A major is a substantial defect below the blocker criteria; a minor has lower impact. Deferral changes disposition, not severity. Apply this even when an earlier report used another label.

## Implementer brief

1. For each addressed finding, provide `Class sweep: scope searched; affected sites; enforcement point; verification; remaining exceptions`. Under `root_cause`, repair the full class within the goal's scope. If the instance is the full class, justify that bound. Checks or warnings close a finding only if they prevent the prohibited behavior. When a class recurs after an instance fix, seek one enforced boundary and a check covering every relevant site, or justify separate boundaries. Honor a required enumeration/design pass before patching again.
2. Maintain coverage for each changed invariant, including consumers and siblings: entry, exit, bypass, failure, timeout, shutdown, and re-entry paths where relevant. Give search scope, queries/results, or the structural bound establishing completeness. Group sites only when the same proof covers them. Use the evidence state matching the proof, and `unverified` for gaps. Your claims inform reviewers but do not substitute for their independent assessment.
3. For every behavioral fix, state `Inverse failure: what this fix could now over-do or under-do; affected paths; regression check`. Add or strengthen a test for that plausible inverse, cite an existing discriminating test, or give a sufficient structural proof where appropriate. For a mechanical fix with no behavioral inverse, explain why it is inapplicable. Check legitimate operation as well as rejection.
4. For shared state, document ownership and lock/permit order; a terminal state is not a lock. For crash/restart-sensitive changes, persist required state and show durable intent before recoverable external effects. Do not add mechanism to compensate for an incomplete inventory.
5. Run assigned validation, honoring `test lifecycle` and `skip`, and report gaps. First-pass tests cover the empty/default case and primary action. For ordinary fixes, execute relevant regression tests and explain which defect their assertions detect. For security-sensitive or reopened behavioral findings, also supply the historical failure or focused fault evidence and replayable patch required by the risk-scaled procedure. A missing required proof stays unverified; never claim an unexecuted historical failure. Keep deliberate breaks in isolated copies, bypass task-result caches for new execution claims, and confirm selectors run the cited tests.
6. Search docs, comments, schemas, and user-visible copy describing changed behavior; check them against recorded decisions. Report scope and discrepancies. Run formatters and lint after behavioral edits and proofs, then re-run affected validation if they change executable code. Report completion only for the final tree.

## Reviewer brief

1. Independently enumerate coverage for every assigned changed invariant. Check consumers beyond the diff, including configuration, deployment wiring, and other languages. Give search scope, queries/results, or a structural bound; an assertion of exhaustiveness is insufficient. Missing inventory bounds require a blocking `enumeration incomplete` finding. Distinguish unknown scope from a known site with unverified behavior. Report every violating row, grouped by proven root cause.
2. Include entry, exit, bypass, failure, timeout, shutdown, re-entry, and siblings from the first review. For persisted state machines, enumerate durable states, transitions, and production callers across success, retry, and conflict; a required transition with no production trigger is blocking. Later incremental reviews inspect both the fix-pass diff and the full task diff. Name each behavioral fix's likely inverse failure and test or prove it using the evidence rules; checking only old findings is invalid. A final fresh-context review starts from the full tree and goal, then reconciles with the ledger after independent assessment.
3. Re-derive, do not inherit. Support `holds (structural)` with your own cited proof of the exact obligation and every relevant site/assumption. Support `holds (executed)` with your own discriminating execution on the actual boundary at this revision. Re-run implementer probes when execution is required; otherwise independently prove the claim or leave it unverified. At least one bounded probe of the riskiest execution-dependent invariant is required even if you find no defect. When all assigned obligations admit structural proof or static review, no token probe is needed. Broader-suite scheduling permits targeted reviewer probes; explicit `skip` or unavailable resources leaves required execution unverified.
4. For shared state, check identity versus recycled IDs, ownership after cancellation/timeout, and lock/permit order in current code and any remedy. Durable intent precedes recoverable effects. Do not treat terminal state as a lock without proving mutual exclusion and ownership, or recommend a lock strategy without checking other acquisition sites. Validate behavior at the boundary that owns it; a substitute cannot prove the property it replaces. For budgets, enumerate the relevant resources, count worst-case work, and compare with enforced charges. Apply the matched watch-lists for domain-specific probes.
5. Use actual validation results for build/type/syntax success claims; a structural proof is not a claim that a compiler ran. Inspect whether tests discriminate the claimed defect. List low-signal tests added/changed or cited as closure evidence: `test | why | harden: <assertion/path> or delete: <why no coverage is lost>`. Tests are required to fix when they are the only evidence for a required invariant or closure; otherwise they are non-required. Delete only if no unique regression protection is lost. Mark insufficient evidence unverified and name the needed proof/check. Claims about dependencies or platforms need pinned source, documentation, or a probe; otherwise label them concerns.
6. Do not change established observable ordering unless `greenfield` or the goal allows it. Distinguish prevention from detection: a still-possible violation leaves the required invariant open. Attach further bypass evidence to its class and reopen disproved closure. Only explicit deferral changes required work to accepted remaining risk.
7. Reuse a ledger ID for the same root cause and name the broader class/causal chain. A shared theme is not enough to merge findings: show that the same fix closes every instance, or retain distinct IDs. Sweep sibling paths. Under `immediate`, report required siblings for explicit deferral. Pre-existing defects are in scope when they break the current goal or changed invariant; list other defects separately and route severe ones as scope-neutral carry-ins.
8. Apply the common severity calibration. For each trust-boundary finding state `exploitable: yes/no` with actor, path, and preconditions; if undecided, write `unverified` rather than guessing “no.” Watch-lists supplement enumeration; use the common reporting format. The critic reports only entries it disputes or finds unevidenced, while still independently checking its riskiest claim.

## Critic brief

1. Re-rate each finding against the common severity calibration and inspect every `major` for exploitability. Report `ID | original → calibrated severity | exploitable? / actor | evidence or missing proof`. Check trust-boundary findings have actor/path/preconditions. This severity audit is part of the critic pass, not a separate mode or substitute for an assigned review.
2. Adjudicate findings, closure evidence, required coverage, and matched watch-lists against the goal and actual code. Scale effort to risk and disputes. Independently test the riskiest claim requiring execution, or re-derive its structural proof when sufficient. Show command/output or proof citations; missing required evidence stays unverified. Purely static obligations need cited review, not invented tests. Do not suppress a finding without contrary evidence or merge findings unless the remedy provably closes both.
3. End with `AGREE`, `DISAGREE_EVIDENCE: <code citation or test result>`, or `DISAGREE_CONCERN: <specific unverified objection>`. State completion and gaps before that line. `AGREE` preserves findings; it does not mean the candidate is ready. A concern cannot suppress a finding or fill a coverage gap.
